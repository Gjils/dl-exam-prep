## 1. Training vs Inference — фундаментальные различия

| Аспект | Training | Inference |
|---|---|---|
| Цель | Обновить веса $\theta$ | Сгенерировать $y$ при заданном $x$ |
| Forward/Backward | Forward + Backward | Только Forward |
| Параллелизм | Батч примеров | Обычно 1 запрос |
| Длина последовательности | Фиксированная (padding) | Переменная |
| KV-cache | Не используется | Используется |
| Точность | fp32 / mixed precision (bf16) | fp16 / int8 / int4 |
| Память (веса) | Веса + градиенты + optimizer states | Только веса |
| Узкое место | Вычисления (FLOPs-bound) | Память (memory-bound) |
| Важно | Throughput (примеров/сек) | Latency (мс/запрос) |

## 2. Autoregressive Generation (авторегрессивная генерация)

### Определение

LLM генерирует текст **по одному токену за раз**, где каждый новый токен зависит от всех предыдущих:

$$
P(y \mid x) = \prod_{t=1}^{T} P(y_t \mid y_{<t}, x)
$$

### Процесс генерации

```
Input: "Столица Франции —"
Step 1: P("Париж" | "Столица Франции —") → выбираем "Париж"
Step 2: P("." | "Столица Франции — Париж") → выбираем "."
Step 3: P("<EOS>" | "Столица Франции — Париж.") → EOS → STOP
```

### Почему это медленно?

- **Последовательное вычисление:** шаг $t$ не может начаться до завершения шага $t-1$
- Каждый шаг — полный forward pass через Transformer (без KV-cache это O($t^2$) для внимания)
- Количество шагов = длине выходной последовательности

### Декодирование

| Стратегия | Описание | Применение |
|---|---|---|
| Greedy | $\arg\max P(y_t)$ | Быстро, но низкое качество |
| Sampling | $y_t \sim P(\cdot)$ | Разнообразие |
| Beam Search | Храним top-B гипотез | Задачи с единственным ответом |
| Top-k/Top-p | Выборка из top-k или top-p | Баланс качества/разнообразия |

(Подробнее — в вопросе [[DL 44 - Декодирование LLM|44]])

## 3. Метрики latency

### 3.1. TTFT (Time To First Token)

**Определение:** Время от получения запроса до генерации первого токена.

**Что включает:**
- Prefill-фаза: обработка входного промпта
- Вычисление всех KV-кэшей для входных токенов
- First forward pass

**Формула:**

$$
\text{TTFT} = \underbrace{t_{\text{network}}}_{\text{сеть}} + \underbrace{t_{\text{prefill}}}_{\text{prefill}} + \underbrace{t_{\text{sample}}}_{\text{выборка}}
$$

**Типичные значения:**
- GPT-4: ~200–500 мс (для коротких промптов)
- LLaMA-7B (4-bit): ~20–50 мс

**Важность:** Критично для **интерактивных** приложений (chatbots) — пользователь не должен ждать >1 сек.

### 3.2. TPOT (Time Per Output Token)

**Определение:** Среднее время на генерацию одного токена после первого.

**Формула:**

$$
\text{TPOT} = \frac{T_{\text{total}} - \text{TTFT}}{N_{\text{output tokens}} - 1}
$$

**Типичные значения:**
- GPT-4: ~40–60 мс/токен
- LLaMA-7B (fp16): ~10–20 мс/токен
- LLaMA-70B (4-bit): ~100 мс/токен

**Важность:** Определяет **скорость появления текста** (комфортно: < 50 мс/токен — ощущается как ввод с клавиатуры).

### 3.3. Total Latency

$$
\text{Latency}_{\text{total}} = \text{TTFT} + (N - 1) \times \text{TPOT}
$$

где $N$ — длина выходной последовательности.

**Пример:**
- Промпт: 100 токенов, ответ: 500 токенов
- TTFT = 400 мс, TPOT = 50 мс/токен
- **Total = 400 + 499 × 50 = 25,350 мс ≈ 25.3 сек**

### 3.4. Throughput

**Определение:** Количество сгенерированных токенов в секунду на всём батче.

$$
\text{Throughput} = \frac{\text{Total tokens generated}}{\text{Total time}} = \frac{B \times N}{\text{TTFT}_{\max} + N \times \text{TPOT}}
$$

где $B$ — batch size.

## 4. KV-Cache

### Идея

При авторегрессивной генерации на шаге $t$ нужно вычислить внимание ко всем предыдущим токенам:

$$
\text{Attention}(Q_t, K_{\leq t}, V_{\leq t})
$$

Без кэша на каждом шаге $t$ мы бы пересчитывали $K$ и $V$ для всех $1 \dots t-1$ заново. Это $O(t^2 d)$ — катастрофически дорого.

**KV-cache** — хранение Key и Value матриц всех предыдущих токенов для **каждого слоя** и **каждой головы внимания**.

### Как работает

**Prefill (Stage 1):**
```
Input: [x₁, x₂, ..., x_N]
Для каждого слоя l:
    K_l = [k₁, k₂, ..., k_N]  → сохраняем в cache
    V_l = [v₁, v₂, ..., v_N]  → сохраняем в cache
    Вычисляем attention для всех токенов разом
Output: последний токен
```

**Decode (Stage 2):**
```
Для каждого нового токена x_t:
    Для каждого слоя l:
        k_new, v_new = compute_KV(x_t)      # только для 1 токена
        K_l = concat(K_cache, k_new)          # append
        V_l = concat(V_cache, v_new)          # append
        attention(Q_t, K_l, V_l)               # O(t × d) вместо O(t² × d)
```

### Размер KV-cache

**Формула:**

$$
\text{KV-cache size} = 2 \times L \times H \times T \times d_h \times \text{bytes\_per\_elem}
$$

где:
- $L$ — количество слоёв
- $H$ — количество голов внимания
- $T$ — количество токенов в кэше (длина промпта + сгенерированные токены)
- $d_h$ — размерность одной головы attention: $d_{\text{model}} / H$
- 2 — для K и V отдельно
- bytes_per_elem: 2 (fp16), 4 (fp32), 1 (int8)

### Примеры расчёта

| Модель | $d_{\text{model}}$ | $L$ | $H$ | $T$ | fp16 | int8 |
|---|---|---|---|---|---|---|
| LLaMA-7B | 4096 | 32 | 32 | 2048 | **1 GB** | 512 MB |
| LLaMA-7B | 4096 | 32 | 32 | 4096 | **2 GB** | 1 GB |
| LLaMA-7B | 4096 | 32 | 32 | 8192 | **4 GB** | 2 GB |
| LLaMA-13B | 5120 | 40 | 40 | 2048 | **1.6 GB** | 800 MB |
| LLaMA-30B | 6656 | 60 | 52 | 2048 | **3.3 GB** | 1.65 GB |
| LLaMA-70B | 8192 | 80 | 64 | 2048 | **6.4 GB** | 3.2 GB |
| GPT-4? (175B) | 12288 | 96 | 96 | 4096 | **~36 GB** | 18 GB |

**Вывод:** Для больших моделей и длинных контекстов KV-cache может занимать **больше памяти, чем сами веса модели**!

### Оптимизации KV-cache

1. **[[DL 43 - Ускорение и сжатие LLM|Multi-Query Attention (MQA)]]:** все query-головы разделяют один K,V → $H_K = 1$
   - Размер: $2 \times L \times 1 \times T \times d_h \times \text{bytes}$ — в $H$ раз меньше
   
2. **[[DL 43 - Ускорение и сжатие LLM|Grouped-Query Attention (GQA)]]:** $H_K$ групп для K,V, где $H_K < H_Q$
   - Компромисс MQA (быстрый) и MHA (точный)

3. **KV-cache eviction:** удаление старых токенов
   - StreamingLLM: сохранять только начальные + недавние токены
   - Sliding window: фиксированное окно

4. **KV-cache quantization:** хранение в INT8 или INT4
   - KIVI: INT4-квантование KV-cache

5. **PagedAttention (vLLM):** KV-cache разбивается на блоки (pages), как в ОС
   - **Непрерывное управление памятью без фрагментации**
   - Возможность sharing между запросами (в beam search)

## 5. Prefill vs Decode — два режима инференса

### Prefill (Stage 1)

| Свойство | Значение |
|---|---|
| Вход | Весь промпт (N токенов) |
| Вычисления | Матричные умножения: $QK^T$ размером $N \times N$ |
| KV-cache | Заполняется |
| Compute-bound | Да (GEMM) |
| Параллелизм | Полный по всем токенам |

### Decode (Stage 2)

| Свойство | Значение |
|---|---|
| Вход | 1 токен за раз |
| Вычисления | Вектор-матричные умножения: $QK^T$ размером $1 \times T$ |
| KV-cache | Читается и дополняется |
| Memory-bound | Да (главный bottleneck — bandwidth) |
| Параллелизм | Нет (последовательный) |

## 7. Batch-эффективность

### Static batching (традиционный)

- Ждём, пока наберётся батч запросов
- Выполняем все вместе
- Проблема: запросы разной длины → padding

### Continuous batching (vLLM, ORCA)

- Запросы добавляются и завершаются динамически
- Каждый шаг — батч из активных на данный момент запросов
- Эффективность: 2–4× лучше static batching

### Split-wise batching (TensorRT-LLM)

- Разделение prefill и decode на разные GPU
- Специализация: prefill GPU (compute-optimized), decode GPU (memory-optimized)

---

## 8. Ключевые выводы

1. **Инференс LLM** принципиально отличается от обучения: только forward, нет градиентов, нужна низкая latency
2. **Autoregressive generation** — последовательный процесс, каждый шаг — один токен
3. **TTFT** (time to first token) и **TPOT** (time per output token) — ключевые метрики качества инференса
4. **KV-cache** — обязательная оптимизация, без неё attention был бы $O(t^2)$ на каждом шаге
5. **KV-cache размер** растёт с длиной контекста: для 70B модели при 8K токенов = ~6.4 GB (fp16)
6. **PagedAttention (vLLM)** — прорывная техника управления KV-cache
7. **Continuous batching** — стандарт для production инференса
