# DL 45 — RAG, длинный контекст и агенты

> **Pipeline (retriever + generator), chunking, когда RAG лучше fine-tuning, длинный контекст (Lost in the Middle), ReAct, tool calling, ограничения**

---

## 1. RAG (Retrieval-Augmented Generation)

### Определение

RAG — подход, при котором LLM генерирует ответ, опираясь на **документы, извлечённые из внешней базы знаний** в момент запроса.

### Архитектура

```
User Query
    │
    ▼
┌─────────────┐     ┌─────────────────┐
│  Retriever   │────▶│  Context Docs    │
│              │     │  (top-k chunks)  │
└─────────────┘     └───────┬─────────┘
    │                       │
    │                       ▼
    │           ┌─────────────────────┐
    └──────────▶│    Generator (LLM)  │
                │  x = [query + docs] │
                └──────────┬──────────┘
                           ▼
                      Generated Answer
```

### Pipeline (подробно)

#### 1.1. Индексация (offline)

```
Documents → Split into chunks → Embed → Store in Vector DB
```

1. **Chunking** — разбиение документов на фрагменты
2. **Embedding** — получение векторных представлений (e.g., text-embedding-ada-002)
3. **Vector DB** — хранение и индексация (FAISS, Pinecone, Chroma, Qdrant, Weaviate)

#### 1.2. Retrieval (online)

```
Query → Embed query → kNN search in Vector DB → Top-k chunks
```

**Методы поиска:**
- **Dense retrieval:** cosine similarity эмбеддингов
- **Sparse retrieval:** BM25 (keyword overlap)
- **Hybrid:** комбинация dense + sparse (реранжирование)

#### 1.3. Generation (online)

```
Prompt = [System + Query + Retrieved Chunks] → LLM → Answer
```

## 2. Chunking (разбиение на чанки)

### Стратегии

| Стратегия | Описание | Размер |
|---|---|---|
| **Fixed-size** | Фиксированное число токенов (с overlap) | 256–512 токенов |
| **Recursive** | Рекурсивное разбиение по разделителям | Адаптивный |
| **Semantic** | По смене темы (LLM-based) | Переменный |
| **Document-based** | По параграфам/секциям | Переменный |

### Важные параметры

- **Chunk size:** 128–1024 токенов (зависит от модели)
- **Overlap:** 10–20% от chunk size (для сохранения контекста на границах)
- **Number of chunks (k):** 3–10 (типично 5)

### Оптимальный размер чанка

| Размер | Плюсы | Минусы |
|---|---|---|
| Малый (128–256) | Больше релевантности | Мало контекста |
| Средний (256–512) | Баланс | — |
| Большой (512–1024) | Много контекста | Меньше точности поиска |

## 3. Когда RAG лучше Fine-Tuning

| Критерий | RAG | Fine-Tuning |
|---|---|---|
| **Новые знания** | ✅ Легко: добавить документы | ❌ Нужно переобучать |
| **Частота изменений** | ✅ Ежедневные обновления | ❌ Редко (раз в месяц) |
| **Достоверность** | ✅ Источник указан в промпте | ❌ Может галлюцинировать |
| **Стоимость** | Низкая (search + LLM) | Высокая (обучение) |
| **Скорость внедрения** | Быстро (часы) | Медленно (дни–недели) |
| **Качество на специфичном домене** | Среднее (ограничен контекстом) | Высокое (глубокая адаптация) |
| **Изменение стиля/формата** | ❌ Плохо | ✅ Отлично |
| **Изучение редких фактов** | ✅ Есть в документах | ❌ Нужны много примеров |

### Практическое правило

> [[DL 45 - RAG, длинный контекст и агенты|RAG]] — когда нужен **доступ к актуальным данным** (новости, документация).
> [[DL 38 - Дообучение LLM|Fine-tuning]] — когда нужно **изменить поведение/стиль/формат** модели.
> **RAG + FT** — идеальный вариант для production.

### Lost in the Middle — Liu et al., 2023

**Экспериментальный факт:** LLM лучше использует информацию в **начале и конце** контекста, но теряет информацию **в середине**.

```
Качество ответа
    ↑
  1.0 │░░░░░░░░░░░░░░░░░░░░░░░░░░
      │░░░░░░░░░░░░░░░░░░░░░░░░░░
  0.8 │░░░░░░░░░░░░░░░░░░█░░░░░░░
      │░░░░░░░░░░░░░░░░░░█░░░░░░░
  0.6 │░░░░░░░░░░░█░░░░░░░█░░░░░░
      │░░░░░░░░░░░█░░░░░░░█░░░░░░
  0.4 │░░░░░░░░░░░█░░░░░░░█░░░░░░
      │░░░░░░░░░░░█░░░░░░░█░░░░░░
  0.2 │░░░░░██░░░░██░░░██░█░░░░░░
      └─────────────────────────────▶
        Начало    Середина    Конец
                 Позиция релевантного документа
```

**Причина:** Ограничение attention (softmax) — длинный контекст "размазывает" внимание.

### Стратегии работы с длинным контекстом

1. **Lost in the Middle mitigation:**
   - Помещать важные документы в начало и конец промпта
   - Использовать "recency bias" — самые важные в конец
   
2. **Структурирование контекста:**
   - XML-теги для разделения секций
   - Bullet points для перечисления
   
3. **Ранжирование релевантности:**
   - Сортировать чанки по релевантности, топовые — в конец
   
4. **Focused attention:**
   - Аннотировать токены документа как "important"
   - Использовать сегментные эмбеддинги

5. **Постепенная обработка:**
   - Recursive summarization
   - Map-reduce подход (суммировать части → суммаризировать суммаризации)

## 5. ReAct (Reasoning + Acting) — Yao et al., 2023

### Идея

Чередование **рассуждения** (reasoning) и **действий** (acting) — модель думает, действует, наблюдает и корректирует.

### Цикл ReAct

```
1. **Thought** (мысль): анализ текущей ситуации
2. **Action** (действие): вызов внешнего инструмента/поиска
3. **Observation** (наблюдение): результат действия
4. Повторять до достижения цели
5. **Final Answer** (ответ): итоговый ответ пользователю
```

### Пример

```
Question: Какова численность населения страны с самым 
            высоким ВВП на душу населения в 2023?

Thought: Нужно найти страну с самым высоким ВВП на душу.
Action: search[GDP per capita 2023 ranking]
Observation: 1. Люксембург (~$132,000), 2. Сингапур, ...

Thought: Уточнить население Люксембурга.
Action: search[population of Luxembourg 2023]
Observation: ~654,768 (на 2023)

Thought: Теперь знаю. Ответ — 654,768.
Final Answer: ~654,768 человек.
```

### ReAct vs CoT

| Аспект | CoT | ReAct |
|---|---|---|
| Рассуждение | Только текст | Текст + действия |
| Использование инструментов | Нет | Да (поиск, калькулятор, API) |
| Взаимодействие с окружением | Нет | Наблюдения |
| Исправление ошибок | Нет (одна цепочка) | Да (цикл) |
| Контроль фактов | Низкий | Высокий (верификация) |

## 6. Tool Calling (Function Calling)

### Определение

LLM может вызывать **внешние функции/инструменты** и использовать их результаты для генерации ответа.

### Формальный процесс

```
User: "Какая погода в Москве и сколько сейчас времени в Нью-Йорке?"

1. LLM определяет, какие функции нужны:
   → get_weather(location="Moscow")
   → get_current_time(timezone="America/New_York")

2. Система выполняет функции:
   → get_weather → "15°C, облачно"
   → get_current_time → "14:32 EST"

3. LLM получает результаты и генерирует финальный ответ:
   → "В Москве сейчас 15°C и облачно. В Нью-Йорке — 14:32."
```

### Определение функций

```json
{
  "name": "get_weather",
  "description": "Get current weather for a location",
  "parameters": {
    "type": "object",
    "properties": {
      "location": {
        "type": "string",
        "description": "City name"
      }
    },
    "required": ["location"]
  }
}
```

### Типы инструментов

| Инструмент | Пример |
|---|---|
| Поиск | Web search, vector DB search |
| Калькулятор | Вычисления |
| API-вызовы | Weather API, DB query |
| Код | Python REPL |
| Файловая система | Чтение/запись файлов |
| Календарь | Планирование встреч |

## 7. Agentic Loops (агентские циклы)

### Простая агентская архитектура

```
User → LLM → Tool call? → Нет → Return answer
               │
               Да
               │
               ▼
          Execute tool → Result → LLM (loop)
```

### Продвинутые паттерны

1. **Reflection:** модель оценивает свой вывод и улучшает
2. **Planning:** разбиение задачи на подзадачи
3. **Multi-agent:** несколько LLM-агентов взаимодействуют
4. **Memory:** долговременная память (прошлые диалоги)

### Примеры фреймворков

| Фреймворк | Особенности |
|---|---|
| LangChain | Композиция инструментов, chains |
| AutoGPT | Автономное планирование |
| CrewAI | Multi-agent оркестрация |
| OpenAI Assistants | Встроенные инструменты |
| Anthropic Tool Use | Нативная поддержка |

## 8. Ограничения RAG и агентов

### Ограничения RAG

1. **Retrieval quality:** если ретривер не нашёл релевантный чанк — ответ будет плохим
2. **Chunking artifacts:** разрыв контекста на границах чанков
3. **Context length:** промпт с чанками может превысить лимит
4. **Latency:** поиск + rerank + генерация = > 2–5 сек
5. **Cost:** каждый запрос с K чанками = дороже
6. **Over-reliance:** модель может слепо копировать из чанков
7. **Contradictory information:** разные чанки могут противоречить друг другу

### Ограничения агентов

1. **Error propagation:** ошибка на раннем шаге портит всю цепочку
2. **Loops:** модель может зациклиться (бесконечные вызовы)
3. **Cost:** много шагов → много токенов → дорого
4. **Reliability:** LLM не гарантирует правильный выбор инструмента
5. **Safety:** модель может выполнить опасные действия (SQL injection, write file)
6. **Prompt injection:** вредоносные инструкции в tool outputs

## 10. Ключевые выводы

1. **RAG** — стандартный метод для доступа к внешним данным: ретривер (search) + генератор (LLM)
2. **Chunking** критичен для качества RAG — размер и overlap имеют значение
3. **RAG лучше FT** когда данные часто меняются; **FT лучше** когда нужно изменить поведение
4. **Lost in the Middle** — модели теряют информацию в середине длинного контекста; важно располагать ключевые факты в начале/конце
5. **ReAct** — чередование рассуждения и действий для многошаговых задач
6. **Tool calling** — естественное расширение LLM для взаимодействия с внешним миром
7. **Агентские системы** мощны, но подвержены ошибкам, зацикливаниям и требуют safety-контроля
